## Реализация

### Часть A. Атомарный счётчик

Реализованы два варианта счётчика в файле `solution/solution.go`:

1. **AtomicCounter** — использует готовую атомарную операцию `atomic.AddInt64` (аналог `fetch_add` в C++)
2. **CASCounter** — реализует инкремент вручную через цикл с `atomic.CompareAndSwapInt64` (аналог `compare_exchange_weak`)

Оба варианта гарантируют корректность при любом количестве горутин без использования блокировок.

#### Почему в Go нет ослабленных порядков памяти?

Авторы Go выбрали последовательную согласованность (seq_cst) для всех атомарных операций в `sync/atomic`, потому что это упрощает рассуждения о многопоточном коде. Ослабленные порядки (relaxed, acquire, release) требуют от программиста глубокого понимания модели памяти и легко приводят к тонким ошибкам. Go следует философии «простота и безопасность» — компилятор и рантайм берут на себя гарантии корректности.

**Что теряется:**
- Производительность на архитектурах со слабой моделью памяти (ARM, PowerPC), где seq_cst требует дорогих барьеров памяти
- На x86-64 разница минимальна, так как процессор сам обеспечивает сильный порядок
- Возможность писать lock-free алгоритмы с максимальной производительностью (например, в ядрах ОС или высоконагруженных системах)

### Часть B. Litmus-тест «буфер записи»

Тест проверяет модель памяти на примере:

в начале: x = 0, y = 0
поток 1: x = 1; r1 = y;
поток 2: y = 1; r2 = x;


Реализация в функции `Litmus(n int, seqcst bool)`:
- **seqcst режим**: использует `sync/atomic` для всех операций — исход `both_zero` невозможен
- **relaxed режим**: использует обычные переменные без синхронизации — исход `both_zero` возможен (намеренная гонка данных)

Для корректного воспроизведения эффекта:
1. Отдельный флаг раунда на каждый поток в разных строках кэша (`PaddedInt64`)
2. Случайная задержка перед критическим участком

**Важно:** Тест `TestLitmus/relaxed` пропускается при запуске с `-race`, так как содержит намеренную гонку данных.

### Часть C. Кольцевой буфер SPSC

Очередь фиксированного размера для одного писателя и одного читателя (`SPSCQueue`):
- Ёмкость округляется до степени двойки (операция `& mask` вместо `%`)
- Голова и хвост в разных строках кэша (выравнивание через `_ [cacheLineSize - ...]byte`)
- `TryPush` и `TryPop` не блокируются — возвращают `false` при невозможности операции
- Локальная копия чужого индекса для избежания чтения чужой строки кэша

go run ./cmd/harness info
